# Submission Requirements

*The real, fillable file is `reference/Submission Template.docx` — this is a guide to what each section needs and why, so drafts can be prepared (in this repo, in docs, wherever) before transferring into the official template.*

## Header

- Project Name, Team Name, all team members
- Problem Statement: **Stress & Workload Manager**
- Video Presentation: unlisted YouTube link
- Presentation Slides: public link

## 1. Project Overview

- **The Problem**: causes as we understand them, who the stakeholders are, at least one similar existing app and why it falls short
- **Our Solution**: 3–4 sentences, then the feature set as a list

## 2. Ideation & Process *(this section carries the most rubric weight — 25% Ideation + parts of Impact)*

**2.1 Ideas We Considered**
- A table of *every distinct idea generated*, each with why it was kept or dropped
- Order so chosen idea(s) are listed first
- Template row shape: `Idea | Why it was dropped / kept`

**2.2 Ideation Boards**
- Embed images directly (preferred) or link to the ideation board
- Don't pad this artificially for "more marks" — reviewers want to see how the team actually thought, messy dropped ideas included
- Add 1–2 lines under each image explaining what it shows
- Any format is acceptable: mindmaps, problem trees, flowcharts, user flows, crazy eights, affinity diagrams, SCAMPER grids, fishbone diagrams, 5 Whys chains, or other sketches
- Markdown embed syntax: `![Mindmap](mindmap.png)`

**2.3 Mentor Consultation**
- Table: `Date | Mentor | Feedback Received | What Was Changed`
- It's fine to disagree with a mentor and say so with reasoning — that still counts as engaging with the feedback (doesn't need to be "we did everything they said")

## 3. Design & Prototype

- UI Prototype: **our Figma board** — https://www.figma.com/design/vAz2Dtc4Xle1BFnbD1YdZM/Assignment?node-id=2005-5 (see `05-figma-prototype.md` for a screen-by-screen description) — **verify it opens in an incognito window** before submitting
- Can be clickable (hyperlinked) or ordered screenshots
- Recommend embedding/linking **4–8 key screens**, each with a caption explaining the interaction

## 4. What Makes It Different

- List novel features, briefly explaining what's original or what the twist is
- Optional: comparison table vs. the existing solutions named in Section 1

## 5. Technical Architecture & Feasibility

- **Tech stack**: frontend, backend, database, APIs/services, hosting plan — for each, explain *why* that choice and what constraints/trade-offs are expected (e.g. "Supabase because it's free, but we'll still need a proxy for X")
- **System architecture diagram**: optional, include if it helps reviewers understand the architecture
- **Build plan & scope**: explicitly state what will be built during the Building Phase if selected as a finalist — a narrow, realistic scope reads as feasible, not as low ambition
